<section id="overview">

## Overview

Cloud Elements is a cloud API integration platform: publish, integrate, aggregate, and manage APIs in one place, with prebuilt connectors, data modeling, and orchestration. The company was API-first. To reach new markets it needed a UI for end-to-end integrations.

I led the experience, managed a designer, worked with three engineers, ran Lean UX workshops, and maintained the Cloud Elements Design System.

<Figure src="images/work/api-integration/hero.webp" alt="Cloud Elements catalog of connectors" caption="The Elements catalog — where an integration starts." />

</section>

<section id="problem">

## API-first was leaving revenue on the table

Enterprise deals were asking for low-code/no-code. Global systems integrators and citizen integrators could not build on an API-only story. That limited growth.

**Solution.** A visual application on the existing APIs: connect services, map data, orchestrate workflows, then debug and administer. Success meant consistent, reusable tooling to sync applications end to end.

</section>

<section id="research">

## Design for Brenda, then tell a three-step story

I kicked off with sales, engineering, product, and leadership on outcomes, persona, and hypotheses, then researched the integrator and the competitive set.

<Figure src="images/work/api-integration/persona.webp" alt="Brenda, global systems integrator persona" caption="Brenda wants to connect systems quickly, with docs she does not have to wade through." />

The product story was three steps: connect services, map data, orchestrate data — plus admin and logging for debug and audit.

<section id="product">

## Connect, map, orchestrate

**Elements.** A catalog to browse services and create a connection. Testing asked what belonged on a service card and whether a code snippet at connect-time helped developers. Users also needed API docs and object lists before they connected.

<Figure src="images/work/api-integration/api-docs.webp" alt="Element API documentation" caption="API docs beside the catalog, so users can inspect objects before they connect." />

**Virtual Data Resources.** One canonical object, many vendor field mappings. A JavaScript editor sat next to the UI for power users. Testing a transformation in place mattered as much as creating it.

<section id="system">

## A system that could wear two brands

We built the Cloud Elements Design System in React Storybook so every surface stayed consistent. That mattered twice: for our own UI, and for SAP, who needed UI5-flavored components on login while Cloud Elements stayed Material-based. SAP used our connectors, mapping, and workflows to power Open Connectors.
